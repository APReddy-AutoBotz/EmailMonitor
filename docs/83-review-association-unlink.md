# Audited association unlink

FR-020 / EM-009/011/012: a reviewer may unlink the selected article-local author/address association and return it to needs-review. This does not merge or split people, delete an observed author, address or citation, attach a new source, change current source policy, or grant new permissions. The action uses the existing association-review role and tenant/source/session/retention fences.

An unlink requires an existing linked author, exact current revision, no replacement author, an explicit reason and the existing ordered evidence identifiers. The resulting revision has no linked author and is marked `needs_review` with `reviewed_unlinked` and ambiguous strength. Retained citations, original observation, author, candidate, and evidence links are unchanged. Audit history contains previous and resulting records and the review reason. Repeating an old revision is a conflict; restoring an accepted association requires a subsequent evidence-backed correction, not reversal of history.

Export snapshots retain their original membership and revision. Existing revision checks make earlier affected exports unavailable, including after subsequent reacceptance. Other current lifecycle, policy and tenant checks remain unchanged. A user must create a new preview and export to reflect the new review state.

Migration `0021_review_unlink` expands only the existing review action and guard for this transition and updates exact schema readiness. It changes no old migration, adds no roles, grants or source capability and does not rewrite prior rows. It is forward-only: old code cannot safely interpret unlink audit history or records, so downgrade requires a separately controlled restore or forward repair. Upgrade, database guard, current-role, concurrency, export invalidation and populated-data behavior require actual PostgreSQL validation. Passing pure-model tests alone is not database acceptance. Live acquisition and cross-observation evidence attachment remain unavailable.

The existing guarded lifecycle browser journey includes keyboard unlink of its retained association, checks that it leaves accepted Contacts, remains in the job's Review queue with its citation, and invalidates the earlier export's download. These authored steps are not a passed result until genuine hosted execution; existing isolation, keyboard and timing guards remain in force.

The separate authored outcome-pagination journey waits for the selected job's terminal replay and resulting render before keyboard navigation, including after returning to Jobs. This preserves the five-second readiness budget and invalidation checks; it does not establish the cause of earlier intermittent failures. The implementation and synthetic regressions are also present in the saved-draft work and need normal reconciliation when the dependent drafts are integrated.

Failure receipts expose only fixed browser isolation stages and installed XML export steps, preserving the original process status and exception. A CSV ready-wait failure may also summarize the existing failure-only publisher and owned-export snapshot in fixed categories; that snapshot is not atomic. These receipts do not expose pages, response bodies, identifiers or assertion text. The installed XML export receipt is also present in the separate job-deletion draft; both copies require reconciliation during later integration. Receipt labels do not establish the cause of a previous failure or replace an acceptance pass.
