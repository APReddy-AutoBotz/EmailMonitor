# 45 — EM-017b reproducible offline packaging prerequisite

## Scope

This is a partial EM-017 engineering prerequisite under documents13/16/21. It packages the existing metadata-only default API library, complete forward-only migration files, built static web assets, schemas, locks and existing notices. It does not assemble the working extraction service, identity provider, tenant foundation, workers or storage. The image's default command states that limited scope and opens no listener. Hosted and dedicated operation must eventually use the same reviewed application artifacts; neither deployment mode is activated by this exercise.

The default API remains explicit scaffold capabilities with extraction/live sources/tenant API false. Three source files alone must import and answer health/capabilities and reject a forged tenant job request in an in-process ASGI probe. Foundation type/exception imports are deferred to the existing explicit injected-foundation branch so no fixture composition enters this minimal image; that existing synthetic assembly and its production refusal remain tested by all prior service gates. This is not a substitute for the product's full runtime assembly.

## Inputs and provenance

Use the already reviewed immutable Python3.12.13 linux/amd64 base in the runtime inventory and unchanged dependency locks. The image builder installs the existing pinned uv tool and locked no-dev dependency closure. The final active virtual environment contains only the evaluated runtime distributions; it does not copy the builder's uv/cache/dev environment. The official base's bundled system tools remain part of that base and are not certified away. Evaluate dependency extras and platform markers through locked uv export, then compare every actual installed distribution/version. In particular, PyJWT's crypto closure is included and unconditional Kombu tzdata remains included even though tzlocal's own edge is Windows-only.

An explicit allowlist creates a private standalone build context rather than using the root diagnostic Docker context, which intentionally includes fixtures. Only api.py/config.py/__init__.py enter the image's application source. No Git directory, tests, identity/source fixtures, environment files, source credentials or host mount is copied. Migration/static/schema components remain separate in the deterministic engineering archive and are excluded from the image build context. The image includes its manifest and current notice/inventory files.

The manifest records the exact source tree, pinned base/platform, evaluated runtime versions, forward migration head and all file sizes/SHA256 values. It explicitly declares working_extraction_service=false and production_ready=false. Archive paths are relative, unique regular files with normalized uid/gid/mode/mtime; links/traversal/unknown migration or web asset types refuse. Archive verification rejects sparse/non-regular members and caps cumulative logical bytes before reading; it checks every manifest field against the trusted Git tree/locked runtime closure, explicit component grammar and migration chain without extracting or executing them. No customer-supplied archive or generic upload/restore interface is introduced.

## Actual acceptance

The separate read-only-token workflow installs only existing pinned tools/locks, builds the actual frontend twice, creates two deterministic archives/contexts and performs two independently uncached Docker builds. It requires equal archive and manifest SHA256 values and equal actual image-content digests. Image IDs are recorded independently; this does not claim byte-for-byte reproducibility of Docker's OCI export/config timestamps. No image registry push, release publication, signing or deployment occurs.

Each owned image runs only a fixed in-process probe under the existing parser-style disposable profile: network none, uid/gid65532, cap-drop ALL, no-new-privileges, default seccomp, read-only root, bounded tmpfs/memory/CPU/pids/file limits, no ports/host mounts/socket/secrets. Inspect before execution, then require actual kernel restrictions, only lo, documentation-target IPv4/IPv6 ENETUNREACH, exact metadata/404 behavior, no imported fixture modules, complete runtime distribution parity and all eight production fixture/stub/outbound/unknown-setting refusals. No listener starts. Unknown or unsupported profile/daemon state fails closed without fallback.

Resource names and ownership labels are unique and registered before possibly ambiguous create/build results. Cleanup reconciles and removes only matching owned containers/images, verifies absence and never prunes caches or unknown resources. BuildKit/base caches are ordinary disposable runner setup; their exhaustive erasure is not claimed. Temporary source contexts/archives are removed with their owned directory. No manual host networking/security setting is changed.

Pure tests cover deterministic metadata, tamper/path/link refusal, migration chain, evaluated markers, exact CI guards, restrictive runtime profile, ambiguous creation cleanup and minimal fixture-free API import. They do not establish actual Docker build/runtime acceptance. New-head actual application/no-skips and all existing six gates plus the new packaging gate remain required.

## Remaining EM-017/018 work

Real IdP/tenant runtime assembly, HTTP/browser/parser/export worker packaging, regional private storage and secrets, supported environment configuration, signed provenance/SBOM/system attribution/vulnerability review, owner-selected distribution license, staging migrations/upgrades/smokes, production backup infrastructure and measured RPO/RTO remain unmet. Migration credentials stay separate; no migration runs at API startup and destructive downgrade is unsupported. EM-015/016 publisher permission/sample gates and EM-WARN-01/intermittent UI cause uncertainty remain unchanged.

The subsequent [EM-017c XML worker package](53-isolated-xml-worker-package.md) is a bounded synthetic-only worker artifact candidate. It adds no embedded repository fixture assets and leaves the metadata image and production refusals unchanged. It does not close the remaining full-service runtime, identity, storage, deployment or source-certification gates above.
