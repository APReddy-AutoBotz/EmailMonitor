# Source search filter contract

FR-004 and FR-006 require the operator to understand the requested search and its limits. The keyword wizard can record a journal and one article type alongside the existing publication date bounds. Changing a field invalidates the current plan. Values are sent explicitly and are shown as requested values, not as evidence that a source applied them. An empty UI field is omitted; a whitespace-only value is rejected. Existing requests without filters keep their previous shape.

The registered synthetic publisher does not declare source-side date, journal or article-type semantics. Planning any of those explicit filters refuses with `fixture_filters_unavailable`, with no discovery start URL. In particular an API request containing an empty journal is a requested filter and is refused, rather than broadened to an unfiltered request. Reuse also refuses a filtered request rather than silently choosing fresh acquisition or ignoring the filter. An omitted journal and the legacy empty article-type list remain omitted filters. These decisions add no migration, source registration, authority or live acquisition.

The internal `source-filter-capability-v1` contract declares date types, exact journal semantics and exact-any article-type semantics without granting permission. An offline authored index exercises the contract with full published calendar dates, exact case-sensitive journals and explicit article types. It applies supported predicates to its complete synthetic index before paging, uses inclusive bounds, and refuses missing, partial or conflicting required metadata. Page and article caps are reported as partial. The index, reported total and outcomes describe only authored fixtures, not an actual publisher or a retained-results postfilter.

The fixture's consistency token binds its index, request and pagination limits for this isolated exercise. It is neither signed nor tenant-authorized and is not a production API cursor. The fixture is not a registered adapter and cannot activate discovery. The existing source planning and policy fences remain in effect.

Real publisher filtering remains unsupported until authoritative source-specific evidence establishes available date types and precision, inclusive boundary behavior, journal and article-type vocabulary and matching, result completeness, stable pagination and applicable policy rights. No source-declared date can be inferred from a generic HTML time element. An implementation must preserve source provenance, current tenant and lifecycle authority, explicit limitations and the existing caps. Local contract and browser-component tests do not establish those publisher semantics, actual PostgreSQL acceptance or installed authenticated browser acceptance.

## Inactive ScienceDirect request description

The official [ScienceDirect Search V2 reference](https://dev.elsevier.com/documentation/SCIDIRSearchAPI.wadl) recommends native PUT; GET is legacy emulation. Its [migration guide](https://dev.elsevier.com/tecdoc_sdsearch_migration.html) documents a publication year or year range in `date`, without establishing range endpoint inclusivity. It documents `pub` as a search over journal or book titles without establishing exact identity or case semantics. `loadedAfter` concerns when content appeared on the platform, not its publication date. The documented request schema provides no article-type field. Therefore none of these fields is equivalent to the application's inclusive calendar-day, exact-journal or article-type filters.

The separate, inactive `sciencedirect_filter_plan` describes native PUT requests with deliberately named provider year and title-search terms. It refuses every requested product filter rather than approximate one. It preserves provider search terms and the original query, permits a conservative subset of the documented year syntax, and accepts only documented page sizes 10, 25, 50 and 100. It will not describe a page crossing the first 6,000 results, even though the guide lists offsets through 6,000. Every plan labels completeness unknown and possible truncation. It creates no transport, adapter registration, credential, response binding, source policy or execution permission; the existing controlled-provider gateway does not use it.

The guide's permitted page sizes conflict with a 200-result maximum listed on the general [API key settings page](https://dev.elsevier.com/api_key_settings.html); the narrower interface-specific limit is used. That page lists a 6,000-result limit, a 20,000-request weekly quota and two requests per second for this API, while stating that actual access and service levels depend on entitlement and terms. These figures are documentation, not a grant or a guarantee of quota, coverage, stable pagination or execution.

The [ScienceDirect access page](https://dev.elsevier.com/sd_apis.html) requires verified entitlement or an approved integration and says open access alone does not grant API access; it directs commercial users to Elsevier. The [use policies](https://dev.elsevier.com/policy.html) are use-case specific; the federated-search policy restricts storage to temporary performance caching. Neither those descriptions nor this request builder establish rights for durable contact harvesting or retained evidence. Live access remains disabled pending an applicable agreement, approved integration, source-policy authorization and separate validation. No publisher API call or content traversal is performed by these tests.
