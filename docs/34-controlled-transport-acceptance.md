# 34 — Controlled synthetic protected transport acceptance

EM-004f wires the shared hop planner into an actual DNS/literal-socket/TLS transport and a separate disposable CI acceptance topology. This remains an explicit test-only assembly; production/default entrypoints refuse acquisition. Full EM-004 stays PARTIAL and EM-006 gated until the reviewed exact-head acceptance evidence is obtained and assessed. No real-source onboarding, extraction, mail, external AI or deployment occurs.

## Transport boundary

`ProtectedGateway` obtains immutable server-composed scope and current-policy callbacks. It authorizes before DNS, queries both complete A/AAAA families, rejects any non-public/mixed/unsupported answer set, selects exactly one literal in the trusted requested family, and reauthorizes before actual TCP. It never uses OS name service, proxy/environment headers, retries, alternate peers, cookies or client body/method controls. HTTPS port is always 443; actual socket peers are compared with the selected literal before and after TLS. TLS requires CA and hostname validation with the original hostname as SNI. The bounded response framing parser rejects duplicate/ambiguous headers and transfer encoding; HTML bytes are capped at 32 KiB in this acceptance assembly. Redirects preserve the original absolute deadline, authorize the new URL before fresh DNS and maintain bounded history. Current policy is rechecked before byte release.

The acceptance resolver uses connected UDP to the immutable synthetic authority on port 5353 with unpredictable query IDs. Its bounded 512-byte authoritative A/AAAA grammar accepts exact questions, full owner names or only the question pointer, and no aliases, truncation, extra records, cache or recursive fallback. Unsupported DNS forms fail closed. This is an actual selected-destination resolver/transport exercised on synthetic hosts; it is not activation of an unrestricted live recursive resolver or publisher connector.

Untrusted browser code remains in the previously verified network-none container. It receives only bounded byte mediation; it cannot choose the tenant scope, DNS route, literal family, CA, credentials or connection options. The trusted gateway has a separate constrained networked container. Its stage callbacks cross owned bounded pipes to the host's actual current PostgreSQL tenant/source authorization; session/database credentials never enter the gateway or fixture containers. The host verifies every callback's exact organization/source/version/operation/host/deadline/redirect scope and again checks current policy before releasing bytes to the browser.

## Fixed disposable topology

The runner's existing Linux amd64 Docker Engine must be version 28 or newer and report built-in seccomp/resource support. Host IPv6 all/default forwarding must already be enabled before construction/build/network creation, verified read-only and rechecked immediately before creation. Unsupported or unreadable values refuse before network creation. The separately approved initialization step is restricted to the disposable GitHub-hosted Linux transport job: it records both existing values, changes only all/default IPv6 forwarding from0 to1, verifies them, and waits for read-only host-state settling before construction captures its unchanged strict baseline. It never configures routes/interfaces, firewall policies or production hosts. The values remain part of the temporary runner configuration until GitHub discards that runner. Moby initializes these host-wide values even for isolated IPv6 bridges, so setup must precede the strict baseline rather than occur as an implicit effect of network creation. See [official Moby forwarding setup](https://github.com/moby/moby/blob/v28.5.2/libnetwork/drivers/bridge/setup_ip_forwarding.go). There is no installation/upgrade, privileged Docker-in-Docker, host networking, added capability, custom gateway seccomp profile, published port, host mount/socket or weaker-isolation fallback. The existing approved browser profile and Chromium sandbox settings remain unchanged.

One uniquely owned internal dual-stack bridge uses both gateway modes `isolated` and disables masquerading. Its immutable IPAM manifest is IPv4 8.8.8.0/29 and IPv6 2001:4860:ffff:ee00::/64. The .1/::1 addresses are reserved metadata only; .2/::2 identify the gateway, .3/::3 fixture A and .4/::4 fixture B. These numerical addresses exist exclusively inside the isolated synthetic network. They are not allocated external resources and must never be contacted through the runner's public route. The unchanged public-address classifier accepts them inside the pinned Python image; no loopback/private-to-public translation or address exception is used.

Before traffic, the harness rejects overlap with existing networks, assigned host addresses and nondefault routes; inspects exact network/endpoint configuration and absence of host bridge addresses or new host routes/rules; and obtains complete guest netlink route/rule dumps. Usable default routes, gateway/nexthop selection, unexpected tables/interfaces or destinations fail closed. Docker itself omits bridge addresses in isolated mode, including daemon-managed IPv6 suppression on that owned bridge. No manual or host-wide sysctl command exists. See [Docker isolated gateway modes](https://docs.docker.com/engine/network/port-publishing/#gateway-modes) and [the version-28 introduction](https://docs.docker.com/engine/release-notes/28/).

Every networked container is nonroot 65532, all capabilities dropped, no-new-privileges, default seccomp, read-only root, bounded 32 MiB temporary filesystem, 256 MiB memory with zero swap, 0.5 CPU, 64 PIDs and bounded file descriptors/core dumps. Guest process/cgroup evidence verifies these restrictions. Only HTTPS fixtures have the namespaced minimum unprivileged port set to 443; no host-wide setting changes. Each container has a closed local DNS upstream with no local upstream listener; internal-only attachment prevents Docker's embedded resolver from forwarding externally. The gateway performs separate literal wire queries to fixture A:5353. See [Docker DNS behavior](https://docs.docker.com/engine/network/#dns-services) and [namespaced container sysctls](https://docs.docker.com/reference/cli/docker/container/run/#configure-namespaced-kernel-parameters-sysctls-at-runtime---sysctl).

Fixture-only CA/leaf keys are generated ephemerally in a bounded temporary build context, never committed or used for external accounts. The gateway image receives public CA certificates only; fixture images receive only their synthetic TLS keys. Images reuse the existing pinned official Python base and locked packages, with no new dependency or license requirement. The browser reuses the existing immutable official Playwright image. Only narrowly assembled source files enter the image contexts; no repository credentials or host environment are copied. Unique ownership labels and names/tags are recorded before creation/build; ambiguous outcomes are inspected and only verified owned resources can be removed. Unknown owners or unestablished absence fail closed without pruning. Owned containers, images, keys and network are removed, their absence checked, and original host address/route/rule state checked after the run. Unsupported inspection or cleanup is a failed acceptance job.

## Required evidence

The distinct controlled transport job must execute all 12 real cases with no skips/warnings: selected IPv4 and IPv6 peers/TLS; fresh redirected DNS selecting a second actual endpoint; mixed/private snapshots with zero HTTP receipts; 403/off-domain/oversize failures without retries; untrusted CA and trusted-CA/wrong-hostname refusal before HTTP; changed DNS unable to alter an already selected literal; and actual sandboxed browser mediation using current tenant SQL policy, cross-tenant/stale-version denial and in-flight revocation before byte release. Existing application, docs, browser and parser jobs remain required. Pure protocol/topology tests are defensive invariants, not substitutes for these actual checks.

The job uses disposable synthetic PostgreSQL roles only on the runner host. No customer or IdP setup is needed. To collect acceptance evidence, use the reviewed Draft's automatic CI; do not run the topology on a user machine or bypass an unsupported runner. Exact commands/results and unmet criteria are recorded in [validation](../reports/em004f-validation.md). Rollback removes this test-only module/harness/workflow; no database migration or production deployment is introduced.
