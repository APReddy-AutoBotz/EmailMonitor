# Publication dates, reuse and association unlink

These decisions resolve the product defaults for FR-004/010/019/020. They do not enable any new source, acquisition authority or live publisher.

## Publication-date requests

Publication bounds are inclusive full ISO calendar dates. The chosen type must be explicit for new UI requests: published, online publication or issue publication. Source-declared raw values and precision must remain visible. A future connector must refuse filtering if it cannot prove the requested type and complete filter semantics; it must not invent a day for a partial date, choose among conflicting dates, or treat an incomplete retained-result postfilter as a complete source search. Missing or ambiguous evidence remains explicit.

The wizard can now record a date type and bounds and invalidates an earlier plan when either changes. The current synthetic connector cannot perform publication-date filtering and returns `fixture_filters_unavailable` without starting discovery. Selecting a date in the wizard does not constitute filtering or a claim that any matching results exist. Existing API requests with date bounds and no type remain valid for compatibility and are still refused by the unsupported connector. Omitting date selection preserves the existing request and idempotency identity. This change adds no migration. Search-filter execution, explicit source declarations and connected filtering acceptance remain future work; generic HTML `time` observations in the current parser are labeled `published` by parser convention and do not independently prove the source explicitly declared the type. Historical retained observations are not rewritten.

The current-authorized retained metadata view can separately annotate each recorded date fact with the precision recognized from its exact text: year, month, full calendar day, or unrecognized. It does not fill missing components, rewrite the fact or citation, certify the parser's date-type label as a source declaration, or select a value when observations conflict. Unsupported or invalid text remains visible and unrecognized. A separate versioned read endpoint wraps the existing authorized metadata with these annotations; the original strict response and schema remain unchanged. The new UI requires the matching endpoint and fails closed when it is unavailable. This annotation is not a discovery filter or evidence of complete search results, and adds no migration or source access.

## Verified observation reuse

Reuse is a deliberate per-job choice limited to verified retained observations in the same tenant within a user-selected freshness cutoff. Current source authority, retention and suppression are checked at use. Reused evidence carries its original observation time and target-local review state; it does not transfer source review decisions. A request for reuse never silently acquires a fresh observation. There is no default freshness period or cross-tenant sharing.

The local candidate supports only three direct authored HTML fixture URLs, and only when the application is explicitly running in synthetic test mode. Other requested routes and production-mode creation refuse. A human-authorized planning transaction selects and binds a current original observation and source batch; the worker later operates on the target-owned copy rather than obtaining cross-job worker authority. Target review begins unresolved, and reuse continuation currently refuses instead of queueing unsupported work. Contacts and outcomes identify reused observations and original time; CSV/XLSX can include snapshot-relative age while legacy rows retain their prior shape.

Migration 0022 adds same-tenant source references, immutable original-only provenance, lifecycle fences and bounded dependent cleanup. Its hard disabled-link constraint was applied and tested first. The separate local migration 0023 removes that constraint for the specifically bounded test candidate. Local migration 0024 adds a private source-item proof that narrows future XML/PDF release checks. Local migration 0025 stages original-bound XML/PDF observation and outcome-binding checks while retaining the existing 0022 non-HTML refusal. The service schema head is `0025_staged_bound_reuse`; older code must not serve it. These migrations are forward-only and require controlled restore or forward repair. No grants or source policies are added. Migrations 0024 and 0025 have not been executed against PostgreSQL. The migrations and API changes have not been published or deployed and must not be treated as release acceptance.

Synthetic PostgreSQL tests have exercised the disabled baseline, cross-tenant and forged-link refusals, independent review and replay, explicit API planning, a human-scoped worker without fresh fixture acquisition, source deletion and expiration fencing and physical cleanup, source-policy revocation, suppression, an invalidated export and the eleven-dependent bounded purge. These tests do not establish all concurrent interleavings, a broker-connected or service-principal worker/publisher, installed-browser acceptance, populated upgrade/restore, or production performance. Actual failure evidence and local validation receipts must accompany any later proposal. A temporary fixture admission timeout did not recur and remains unexplained. No live source, production migration or real user-data deletion has occurred.

`test_service_reuse_tenant.py` authors a separate genuine-CI-only service worker case: after human-scoped materialization it checks that the target delegation can read the target but not the source, then processes the target without fixture acquisition and checks independent review. `test_service_reuse_broker.py` authors a crash, original redelivery and recovery case, and the installed operator journey has an additional explicit reuse case. They use the existing isolated service fixtures and CI guards; local collection and skips do not establish their execution.

The local preparation contract now retains the exact original JSON and validates XML/PDF's original organization, job, execution item, generation, policy and discovery bindings against the source observation and completed source batch. It rechecks that source before a target write. The local quality and metadata projection path can use the original binding only after checking the current-authorized source batch, original row, digest, payload and item; it rechecks them at release. The provider and tooltip paths refuse an explicit reuse request if retained input is missing or unresolved, before opening a transport or browser. These checks have controlled-fake tests and do not enable any new adapter or establish actual database authority.

The closed adapter classifier recognizes only the existing authored HTML, XML/provider and PDF fixture identities and respects the PDF option and current input filters. Classification itself is not source authorization or permission to acquire. The shared materializer accepts a matched adapter internally and binds the source selection to it; its public entry point and planning still admit only the existing HTML reuse slice, and the database independently refuses XML/PDF links. Controlled-fake tests of the shared selector do not establish permission or persistence. Partial, unsupported or browser-unresolved source evidence is refused rather than promoted to a complete observation.

Completing non-HTML reuse requires the staged database changes to be verified and a narrowly scoped adapter admission path to be implemented. The original observation trigger requires an XML/PDF binding to the target running item, whereas honest reuse must preserve the original source-job binding; the SQL outcome/export binding likewise originally expected the current job's binding. Migration 0025 stages a reuse-specific source proof and outcome binding; a static contract verifies the ordinary observation predicates remain identical and the original non-HTML refusal remains. Actual SQL proof must establish original item and content, target fences, locking, lifecycle cleanup, immutable export behavior and all negative cases before any refusal is changed. The API still refuses these adapters. This is a remaining engineering and validation task, not an unresolved product choice or permission to activate live acquisition.

## Evidence correction and unlink

Unmerge means an audited, reversible unlink of the selected author-address association into unresolved review, using revision checks, current reviewer authority and existing export invalidation; it does not split people or delete source evidence. Attaching evidence requires its own valid observation and source/tenant provenance. The bounded unlink implementation and its validation limits are described in `docs/83-review-association-unlink.md`; cross-observation attachment remains unimplemented. Existing role restrictions remain in force.
