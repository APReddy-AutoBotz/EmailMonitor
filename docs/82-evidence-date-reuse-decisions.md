# Publication dates, reuse and association unlink

These decisions resolve the product defaults for FR-004/010/019/020. They do not enable any new source, acquisition authority or live publisher.

## Publication-date requests

Publication bounds are inclusive full ISO calendar dates. The chosen type must be explicit for new UI requests: published, online publication or issue publication. Source-declared raw values and precision must remain visible. A future connector must refuse filtering if it cannot prove the requested type and complete filter semantics; it must not invent a day for a partial date, choose among conflicting dates, or treat an incomplete retained-result postfilter as a complete source search. Missing or ambiguous evidence remains explicit.

The wizard can now record a date type and bounds and invalidates an earlier plan when either changes. The current synthetic connector cannot perform publication-date filtering and returns `fixture_filters_unavailable` without starting discovery. Selecting a date in the wizard does not constitute filtering or a claim that any matching results exist. Existing API requests with date bounds and no type remain valid for compatibility and are still refused by the unsupported connector. Omitting date selection preserves the existing request and idempotency identity. This change adds no migration. Search-filter execution, explicit source declarations and connected filtering acceptance remain future work; generic HTML `time` observations in the current parser are labeled `published` by parser convention and do not independently prove the source explicitly declared the type. Historical retained observations are not rewritten.

The current-authorized retained metadata view can separately annotate each recorded date fact with the precision recognized from its exact text: year, month, full calendar day, or unrecognized. It does not fill missing components, rewrite the fact or citation, certify the parser's date-type label as a source declaration, or select a value when observations conflict. Unsupported or invalid text remains visible and unrecognized. A separate versioned read endpoint wraps the existing authorized metadata with these annotations; the original strict response and schema remain unchanged. The new UI requires the matching endpoint and fails closed when it is unavailable. This annotation is not a discovery filter or evidence of complete search results, and adds no migration or source access.

## Verified observation reuse

Reuse must be a deliberate per-job choice, limited to verified retained observations in the same tenant within a user-selected freshness cutoff. Current source authority, retention and suppression must be checked at use, and reused evidence must carry its own lineage, observation time and age. Requested fresh acquisition cannot be silently replaced; the user retains an acquisition option. Review decisions and audit history are not transferred by matching DOI. This is the selected contract, not implemented reuse. No default freshness period or cross-tenant sharing is implied.

The local foundation adds an explicit `verified_retained` request and an offset-qualified cutoff, normalized to UTC; omitting it preserves the old request identity. The wizard labels the cutoff as UTC, clears old plans when it changes, and states that reuse is unavailable. After the normal acquisition authorization check the server refuses such requests before creating a job or idempotency record; it never substitutes fresh collection. A pure offline draft reconstructs job-specific, initially unaccepted associations from authored observation facts rather than copying a reviewed batch. This draft does not prove tenant ownership, current authority, freshness or retention, and is not wired to execution or persistence.

Executable reuse still needs a durable, transactionally verified source-to-target observation lineage that retains the original observation time, independent job-local review state and audit history. The implementation must recheck the cutoff, tenant, current source policy, retention, suppression and lifecycle fences at use, and handle replay and concurrent revocation or deletion without transferring acceptance. The existing same-job observation foreign key and parent fences cannot establish these properties for another job. Actual PostgreSQL concurrency and lifecycle tests and connected installed acceptance remain required. No source is assumed to have supplied a publication date merely because its parser assigned a label.

The isolated lineage draft models the original source job, target job, source and article identity, observation revision, policy and generation, separate acquisition and content digests, and original observation/expiry times. Its inclusive cutoff check refuses future or expired candidates, but is only a pure consistency check on supplied values; it cannot attest a database row or current permission. Executable storage must obtain and verify these values from the locked source observation and target work in the same transaction, never regenerate `observed_at` by reinserting an observation. It must create a distinct target-owned batch and retain a reference to its source; copying the continuation's inherited batch would share mutable review decisions. Exact source revision, both jobs, deletion generation, current source-policy and privacy/retention state must be fenced on use and on later review, result and export reads. A deleted, expired, suppressed or revoked source must fail closed without reviving evidence. Existing job/item and source filters, immutable exports, quota accounting, audit history and old non-reuse records must retain their existing behavior. The exact database locking order and source-deletion/retention handling remain implementation and real-PostgreSQL proof obligations, not claims made by this draft.

A real disposable PostgreSQL baseline now exercises the existing runtime role: a target job cannot acquire a batch by copying the source job's batch row; the current parent fence refuses it and preserves the source review. The pure draft derived from that retained HTML observation starts a distinct unresolved association. This is evidence of the current refusal, not persisted reuse, tenant-concurrency proof, or approval to weaken the fence. The first test of the request refusal also proved the 409 and absence of new job/idempotency rows before failing an unrelated test assertion about the shape of a successful fresh plan; the corrected full test passes on a replacement disposable instance.

A local transaction-scoped preparation function now constructs a target-specific unresolved draft and replay digest from a selected retained source using the existing target scope, source-batch fence, ordinary RLS reads, matching policy and freshness checks, with a final source/target/expiry recheck. It is not connected to a route or worker, does not create or store a target batch, and has only controlled-fake tests. In particular, the current extraction service delegation is scoped to the target job: `service_batch_visible` and `service_read_batch` do not authorize a batch owned by an earlier job, even in the same tenant. A safe worker path needs a narrowly bound source delegation or equivalent current-authority design and real PostgreSQL proof. The preparation function does not itself provide that authority, establish a correct lock order, or make retained reuse executable.

A further local draft explores materializing a single exact authored HTML observation during planning under the requesting human's existing tenant authority, so a later worker reads its own target job rather than a different job's batch. It chooses an eligible retained source deterministically, retains the selected source on replay, refuses missing sources without acquiring new data, and has a target-specific initial association mapper. This draft is unreachable and requires database columns and guards not yet implemented. Copying the source observation also creates a physical retention dependency: source revocation or deletion must immediately fence the target, and source expiry/deletion must remove the copied observation, review content and derived artifacts in bounded, restart-safe steps. The current inherited-batch lifecycle only fences dependent jobs; it does not prove this separate copy is purged. A source link or a visibility-only check is insufficient. This proposed path must remain disabled until lifecycle, export, worker and database race invariants are implemented and tested; current normal extraction retains its original mapping.

For the fixture worker's article path, the local candidate checks the authorized job request before loading fresh fixture bytes when no retained observation is visible. An explicit reuse request is refused at that point; omission preserves fresh fixture behavior. This is defense in depth, not proof of all dispatch routes or durable reuse. It adds a database authorization read to the missing-observation path and needs actual worker/SQL and timing acceptance before publication.

## Evidence correction and unlink

Unmerge means an audited, reversible unlink of the selected author-address association into unresolved review, using revision checks, current reviewer authority and existing export invalidation; it does not split people or delete source evidence. Attaching evidence requires its own valid observation and source/tenant provenance. The bounded unlink implementation and its validation limits are described in `docs/83-review-association-unlink.md`; cross-observation attachment remains unimplemented. Existing role restrictions remain in force.
